## 1. Original Idea

## 2. Analysis & Scope

The repository already has `prisma/seed-all.sql`, which is the canonical one-file development
dataset, but it currently contains only 8 representative `entity_images` rows. The complete
52-image dataset is available only through the TypeScript manifest plus an Internet-dependent
command. This follow-up will make the SQL file genuinely self-contained: after migrations, one SQL
execution will seed the full demo database, including all image URLs and attribution metadata,
without requiring Node.js or Internet access.

**In scope:**

- Upgrade the existing canonical `prisma/seed-all.sql`; do not create a second duplicate
  full-database seed that could drift.
- Include the complete current image fixture set:
  - 34 Province cover images;
  - 12 Category cover images;
  - 6 demo Place cover images.
- Embed the already validated Wikimedia Commons image URLs and metadata directly in SQL:
  source-page URL, alt text, author when available, license name/URL, dimensions, and
  `sortOrder = 0`.
- Keep all existing development fixtures in the same file: users/auth support rows, Provinces,
  Categories, Places, links, Posts, Reviews, Comments, Reactions, and rating aggregates.
- Make image inserts safely repeatable whether the image row was previously created by SQL or by
  `npm run db:seed:images`.
- Add SQL validation that fails the transaction if any expected Province, Category, Place, or
  image relation is missing.
- Keep clear execution instructions for both `psql` and `npx prisma db execute`.
- Add a read-only final summary that reports image counts by owner type.
- Validate the file statically and, when PostgreSQL is available, execute it twice to confirm
  syntax, integrity, and idempotency.

**Out of scope:**

- Schema, migration, Prisma model, API, DTO, Swagger, service, or authorization changes.
- Fetching new image URLs from the Internet or changing the approved 52-image selection.
- Downloading images or copying them to S3/R2.
- Adding Post/Review media tables or additional galleries.
- Production data, production credentials, destructive reset/truncate behavior, or automatic
  execution during application startup.
- Rewriting historical prompt `006` or `008`; this prompt is the audited follow-up.

**Assumptions** — approval of this draft confirms these choices:

- “Dễ dùng” means maintaining one authoritative file, `prisma/seed-all.sql`, runnable with one
  command after migrations.
- The file targets the latest checked-in PostgreSQL schema, including migrations through
  `20260728040000_post_description_html_content`.
- The SQL remains development-only and retains the existing documented
  `admin@example.com` / `Admin@123456` login.
- Image URLs are frozen snapshots of the 52 links already live-validated in prompt `008`.
  `npm run db:seed:images` remains available when the team wants to refresh remote metadata later.
- The script is additive/idempotent: it updates deterministic fixture rows and does not truncate
  or delete unrelated application data.

## 3. Proposed Technical Details

Implementation will follow the database safety and naming rules in `docs/02-code-standards.md`.
The current Prisma schema and migrations are authoritative.

### 3.1 Entity / Schema changes

- No schema or migration changes.
- Modify data statements only in `prisma/seed-all.sql`.
- Continue writing the existing `entity_images` fields documented in
  `docs/04-database-schema.md`.

### 3.2 API Endpoints

No API changes.

| Method | Path | Auth/Role | Description |
|---|---|---|---|
| N/A | `prisma/seed-all.sql` | Direct PostgreSQL execution | Seed the complete development dataset, including 52 image links |

Supported execution forms remain:

- `psql "$DATABASE_URL" -X -v ON_ERROR_STOP=1 -f prisma/seed-all.sql`
- PowerShell equivalent using `$env:DATABASE_URL`.
- `npx prisma db execute --schema prisma/schema.prisma --file prisma/seed-all.sql`

### 3.3 Key DTOs

- No DTO changes.
- SQL fixture fields must match the current Prisma/database column names exactly.

### 3.4 Important business rules

- The entire file remains inside one `BEGIN`/`COMMIT` transaction.
- Use owner-specific image upsert statements so PostgreSQL can target the correct unique key:
  - `("provinceId", "sortOrder")`;
  - `("categoryId", "sortOrder")`;
  - `("placeId", "sortOrder")`.
- Resolve owners by stable slug instead of assuming UUIDs generated by another seed command.
- On conflict, update URL, provenance, alt text, author, license, dimensions, and `updatedAt`,
  while preserving the existing image row ID.
- Province/Category/Place fixture IDs remain deterministic for clean-database runs.
- Do not write generated `search_text` columns; PostgreSQL maintains them automatically.
- Validate before commit that:
  - all 34 expected Province slugs exist;
  - all 12 expected Category slugs exist;
  - all 6 expected Place slugs exist;
  - every one of those 52 owners has its `sortOrder = 0` image;
  - every seeded image has exactly one owner, an HTTPS image/source URL, non-empty license name,
    and valid positive dimensions.
- The summary reports total rows plus image counts split into Province, Category, and Place.

### 3.5 Side effects / Async jobs / Cache invalidation

- Explicitly executing the SQL inserts or updates development fixture rows.
- Direct SQL bypasses NestJS events, queues, and cache invalidation.
- No Internet request occurs during SQL execution because URLs and metadata are embedded.
- Existing aggregate-recalculation SQL remains responsible for seeded Place ratings.
